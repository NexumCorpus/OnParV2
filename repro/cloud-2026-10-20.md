billing does not match the code path.

## Do the CI commands match the README's?

Mostly, with three differences that matter:

1. **The e2e step never runs in CI.** In `.github/workflows/ci.yml` the step is
   `if: env.SUPABASE_E2E_URL != ''`. No workflow-, job- or step-level `env:`
   defines `SUPABASE_E2E_URL`; the step's own `env:` maps the secret to
   `NEXT_PUBLIC_SUPABASE_URL`. So the condition is always false. Confirmed on
   the HEAD run
   [actions/runs/39313030184](https://github.com/NexumCorpus/OnParV2/actions/runs/39313030184)
   (job `e2e-tests`): `Run npm run test:e2e` has conclusion **skipped**, yet the
   job and run are **success**. The green check implies an e2e result that was
   never produced.
2. CI runs `npx playwright install --with-deps` before e2e. The README does not.
3. CI runs `npm test -- --coverage`, which enforces 70 % thresholds. The README
   runs plain `npm test`. CI builds with explicit placeholder env vars instead
   of `.env.local`. Both pass here.

`npm ci` (CI) vs `npm install` (README) made no difference: the lockfile was not
modified.

## Numbered gaps

1. **`npm run test:e2e` cannot pass from the README alone.** The README never says
   to run `npx playwright install` (CI does). On this VM the literal command fails
   28/28.
2. **Even with a browser, `Dashboard › navigation links work` fails** (×2
   projects). It needs a signed-in session, but the README presents `test:e2e` as
   a gate with no Supabase or test-user prerequisite.
3. **CI's e2e gate is a no-op that reports success** (see the CI section above).
   A stranger reading the green check cannot tell e2e never ran.
4. **Most e2e specs assert nothing in practice** (code read, plus the page
   snapshot from run 9b):
   - All 6 `inventory.spec.ts` tests open `/dashboard/inventory`. The real route
     is `/inventory` (`app/(dashboard)/inventory/page.tsx`; route groups add no
     URL segment), and every assertion is behind `if (await x.isVisible())`.
   - 3 of 4 `dashboard.spec.ts` tests are guarded the same way.
   - So 18 of the 26 "passed" results executed no assertion. Names such as "waste
     event atomically decrements inventory quantity" and "soft-deleted items do
     not appear" describe behaviour that is never checked.
   - Only the 4 `auth.spec.ts` tests (×2 projects) make real assertions, and they
     pass.
5. **"checkout then reports 'Billing is not configured'"** does not match the code.
   The UI shows the generic "Something went wrong. Please try again." (C9). The
   copy-paste flow also leaves `STRIPE_SECRET_KEY` non-empty, so "leave it empty"
   needs a manual edit the README does not spell out.
6. **`npm run dev` dirties a tracked file** (`next-env.d.ts`), so `git status` is
   not clean after following the README.
7. **The ten-second demo covers 7 of the 10 surfaces** in the README's table.
   Suppliers, Analytics and Onboarding/settings are absent.
8. **Supabase steps 1–3 (create project, run SQL, sign up, sign in, use the app)
   were not verifiable** without a Supabase account. The SQL was exercised only
   against a hand-written stub of Supabase's `auth`/`storage` schemas on vanilla
   Postgres 16, which proves it parses and runs, not that it behaves the same
   under Supabase.
9. **The deployed-app health claim in RECOVERY.md was not verifiable from this VM**
   (egress blocked). This report makes no claim either way about whether the app
   is up.
10. **"Stripe integration points", "Sentry instrumentation" and "structured
    logging"** were confirmed only as present in code and dependencies. No
    Stripe, Sentry or webhook call was exercised.

## Other observations (not README claims)

- **`/forgot-password` is unreachable when logged out.**
  - `proxy.ts:5` `PUBLIC_ROUTES` omits `/forgot-password`, so the proxy sends
    unauthenticated visitors to `/login`.
  - Observed with placeholder env: HTTP 307 → `/login`, and in Chromium the
    final URL is `/login`.
  - Code read for real Supabase: the `!user` branch sends them to
    `/login?redirect=/forgot-password`.
  - The login page's "Forgot password?" link therefore loops back to login.
  - Code read only: `resetPasswordForEmail` uses `redirectTo: <origin>/login`, and
    no page calls `auth.updateUser`, so even a delivered reset link never asks
    for a new password.
- **`npm audit`: 1 critical** in the pinned `next@16.1.6` (advisory range
  `9.3.4-canary.0 – 16.3.7`). There are also 18 highs, including
  `eslint-config-next`.
- `/api/health` reports `"version":"2.0.0"`; `package.json` says `0.1.0`.
- `next build` prints a level-50 error log for an expected Next.js
  `DYNAMIC_SERVER_USAGE` signal caught in `getPurchaseOrders`, which reads like a
  failure in build output.
- With placeholder env, submitting the login form surfaces the raw
  `Invalid supabaseUrl: Must be a valid HTTP or HTTPS URL.` toast. That is
  expected, but the README does not warn about it.
- `.gitignore` contains `.env*`, which also matches the tracked `.env.example`.
  It is harmless while the file stays tracked.
